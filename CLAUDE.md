# Half-Life movement for Clair Obscur: Expedition 33

A UE4SS Lua mod that gives Clair Obscur: Expedition 33 a first-person camera and Half-Life 1 movement (bunny hopping by holding jump, air strafing) while exploring.

## Never commit

- Anything taken from the game or a player's PC: extracted game files, UE4SS dumps (CXXHeaderDump, UHTHeaderDump, ObjectDump), `.usmap` mappings, logs, crash dumps, save games. `.gitignore` covers the usual names.
- Code from the Half-Life SDK: its license limits it to Half-Life mods. `physics.lua` is an independent implementation of the Quake/Half-Life movement model; keep it that way.

## Layout

- `HL1Movement/`: the folder players copy into `...\Sandfall\Binaries\Win64\ue4ss\Mods\`. `enabled.txt` makes UE4SS load it without editing `mods.txt`.
  - `Scripts/main.lua`: entry point. Settings, hotkeys, hooks, and the per-frame checks of when the mod may act.
  - `Scripts/config.lua`: player settings, in Half-Life units.
  - `Scripts/hl1movement/`: `physics.lua` and `settings.lua` (pure Lua), `movement.lua`, `view.lua` (which camera the game shows, and when first person may be on), `camera.lua`, `input.lua`, `overrides.lua` (remembers and restores game values), `journal.lua` (the list of changes that survives a UE4SS mods restart), `guard.lua` (runs each step on its own and logs its errors), `ue.lua` (safe UE4SS helpers), `log.lua`, `diagnostics.lua` (the report).
- `tests/`: `lua5.4 tests/run.lua`. `fake_game.lua` stands in for UE4SS and the game, closely enough to run `main.lua` frame by frame, with E33's camera set-up (several cameras on the character; Unreal shows the first active one).
- `docs/TESTING.md`: checklist for testing in the game, the console check, what to send, Remote Desktop.

## Checks before committing

`lua5.4 tests/run.lua` and `luacheck .` must both pass (Ubuntu packages `lua5.4` and `lua-check`). The GitHub Actions workflow runs both and uploads the mod folder as an artifact.

## Decisions so far

- **Lua only.** A UE4SS C++ mod needs the private UEPseudo repository (a GitHub account linked to Epic) and must be rebuilt for each UE4SS build.
- **UE4SS experimental builds.** The game is UE 5.4.4, which the stable 3.0.1 doesn't support. Point players to experimental-latest; builds from 1176 avoid the soft-pointer crash (issue 1433). Keep the code working on build 848 and later:
  - compare objects with `GetAddress()`, never `==`;
  - copy structs through tables, never struct to struct;
  - don't rely on `LoopInGameThread*` or EngineTick: `EngineTickAvailable` may be false, and then `ExecuteInGameThread` throws;
  - UE4SS's own methods (`IsValid`, `GetWorld`, `GetFullName`, `IsA` and so on) shadow UFunctions of the same name;
  - always call game functions with `:` and every parameter; an out parameter takes a table, which UE4SS fills under the parameter's reflected name (`out.MainCamera` for `GetMainCamera`; SDK dumps show `MainCamera_0` because Dumper-7 renames parameters that share a member's name, so check a dump's `CallFunc_<Function>_<Param>` locals for the real name); a struct out parameter such as `FHitResult` is filled field by field, fields without a handler are skipped;
  - reading a field a struct doesn't have raises an error (read struct fields one at a time with `ue.get`/`ue.number`);
  - a `uint8` property (ByteProperty, such as ALS's `bRequestMovementSettingsChange`) is written with `lua_tointeger`, so a Lua `true` stores 0: write numbers;
  - `GetClass` on a null object crashes the game instead of raising an error, so `ue.className` and `ue.fullName` check `IsValid` first;
  - `ModRef:SetSharedVariable`/`GetSharedVariable` survive a mods restart and take nil, booleans, numbers, strings and objects. `ModRef.OnUnload` only exists from build 1181 and runs off the game thread, so it isn't used.
- **Hooks.** A post-hook on `BP_jRPG_Controller_World_C:ReceiveTick` drives every frame: it runs after input and before the character's movement tick. The fallback is the character's `ReceiveTick`, which runs after the movement component (`bTickBeforeOwner`), too late to take the input away: with it only first person runs, and the log says so. Blueprint classes only load with a save, so hooks are added at load, at each `PlayerController:ClientRestart`, and from key callbacks while the frame hook is missing (F7 always tries the jump hook too), never from inside a hook: UE4SS's `script_hook` iterates its hook list by reference while it runs a callback, and `RegisterHook` appends to that list (use after free). Key callbacks may register hooks because UE4SS holds its recursive Lua lock (`m_thread_actions_mutex`) for them and for every script hook. Before `RegisterHook`, the function is looked up with `StaticFindObject`, because a failed `RegisterHook` leaves a Lua thread behind. UE4SS runs the native `ClientRestart` callback without its lock, so that callback only adds hooks and sets a flag; the old character is put back on the next frame.
- **Hotkeys only queue their action;** the frame hook runs the queue. Keybinds run on UE4SS's input thread, and acting on a key during a level load crashed another E33 mod. The key callback itself only does what doesn't touch the game: adding missing hooks, and for F7 reading `config.lua`. Before the frame hook exists, the action goes to `ExecuteInGameThread`. With no frame hook, F5 hooks in and turns the mod on. F5, F6 and F7 retry everything, including the engine's first-person view where it failed. F8 only asks for the report; it is written at the end of a frame, not during the area-change wait or the 3 s settle. With the mod switched off or turned off by its errors, and with a character the mod leaves alone, it still waits for an area change to end and for a new character's first 3 s (a settle under way when the mod is switched off goes on), though not for 3 s after an area change that kept the character. It waits at most 10 s after the first press: pressing again doesn't start the wait again. The mod's clock goes on after it turned itself off, so these waits end. Before a save is loaded it reads nothing of the game: no `FindFirstOf`, which searches every object while the game may be loading. After the mod turned itself off, the report uses the controller of the frame it is written in.
- **Errors.** `guard.lua` runs each step on its own: the camera, the movement, turning the character, hiding the body, the pitch limits, the view check, the speed limiter. A step that fails 30 times in a row is turned off with its clean-up, without the others. Each different error is logged once (at most 20 lines until F5 or F7). The whole-frame breaker (30 failed frames turn the mod off) stays for the rest.
- **Movement.** Each frame the mod:
  - consumes the character's movement input (`ConsumeMovementInputVector`), so Unreal doesn't accelerate on its own; `GetCurrentAcceleration` on the next frame tells if game input still reached the movement component (logged, not fixed);
  - works out the Half-Life velocity from the current `Velocity` and writes it back, in fixed steps of `1/PhysicsRate` s (default 100 per second, Half-Life at fps_max 100; `physics.simulate`): leftover time carries to the next frame, the view yaw is spread over the steps the short way round, at most 25 steps a frame, a jump only on the first step (or at once in a frame too short for a step). One step per frame lost air strafing speed below about 45 fps. `PhysicsRate` stops at 250: 25 steps cover a frame of 0.1 s, the longest the mod counts;
  - jumps with `SetMovementMode(3, 0)` plus Z velocity, and adds only the moving platform's velocity, read before the mode change with `GetImpartedMovementBaseVelocity` (falling back to the change `SetMovementMode` made); anything else the mode change did to the velocity is logged and ignored, since the speed limiter listens to mode changes. With the movement component's `bStayBasedInAir` (engine default false; shown in the report), Unreal keeps carrying the character with its base and adds nothing, so the mod adds nothing either, and still logs and ignores what else the mode change did;
  - takes the platform's velocity (`GetImpartedMovementBaseVelocity`, read on the first frame on the ground) out of the velocity at a landing, as leaving the platform put it in (not with `bStayBasedInAir`): Unreal carries a based character with its base and leaves the velocity as it was in the air, so the platform's motion counted twice, and each hop on a moving platform added its speed again (0.2 to 0.2.3). The hop lines give the speeds over the ground at take-off and landing (with `bStayBasedInAir`, relative to the platform, which then goes on carrying the character in the air);
  - cancels braking: `bUseSeparateBrakingFriction = true` and `BrakingFriction = 0`, which also beats ALS's raised `BrakingFrictionFactor` after landing; `BrakingDecelerationWalking/Falling = 1`, not 0, because ALS's anim instance divides by `GetMaxBrakingDeceleration()`; takes out ALS's `CurrentMovementSettings.MovementCurve` every frame (the curve drives ground acceleration, braking and friction, and its braking would cost speed on each landing frame); and adds back `GetMaxBrakingDeceleration() * dt`;
  - sets `MaxWalkSpeed` huge every frame, because ALS and the game rewrite it (each rewrite is logged, the first 3), and keeps the game's value for that frame's cut check; checks once that `GetMaxSpeed()` follows it;
  - pauses the speed limiter `BP_VelocityControllerComponent_C` (the character's `BP_VelocityControllerComponent` property, or found among its components), checked every frame: it clamps to `GetMaxSpeed()` and is wired to `MovementModeChangedDelegate`, so it can come back on at every jump and landing;
  - with `KeepSpeed` (default), undoes a speed cut: the horizontal speed read back at most 97 % of what the mod wrote last frame, with the direction within 2°, although the character moved at least 90 % (and at most twice) of the way that velocity would take it in that frame, and the speed read back is under 97 % of the speed it really moved at (`K2_GetActorLocation` before and after, minus the velocity of the moving platform it stood on when the mod wrote, from `GetImpartedMovementBaseVelocity` read then: Unreal moves a based character with its base, apart from its velocity; a platform that reports no velocity, such as one moved without a movement component or physics, still counts, as in 0.2.1). Walking off a ledge, the speed expected is what the mod wrote plus that platform's velocity, which Unreal adds then, as at the mod's jump (not with `bStayBasedInAir`). Unreal walks a frame over `MaxSimulationTimeStep` (0.05 s by default, so under 20 fps) in several moves, which can take the character from a moving platform onto still ground and then off its ledge, and then adds nothing: so a speed that comes back as the mod wrote it isn't a cut either, and a cap at the mode change that leaves between 97 % of the mod's speed and 97 % of that plus the platform's isn't undone. Walls and slopes turn the velocity; a wall hit head on or a failed step-up shortens the move, and `PhysWalking` then sets the velocity from the distance moved, so neither counts. The distance isn't checked when the movement mode changed during Unreal's update (a landing, walking off a ledge): the limiter's handler of that change may cap the speed inside the move, before the rest of the frame is walked at the capped speed; a wall hit in such a frame counts as a cut for that one frame, and so would a game launch that keeps less of the speed (none is known in E33). Below 20 % it only counts if the limiter had just been started again or the speed is `GetMaxSpeed()` or a `MaxWalkSpeed` the game wrote since the last frame (within 1 %, 3D or horizontal); otherwise it is the game stopping the character. Cuts are logged (the first 5, with GetMaxSpeed, MaxWalkSpeed and the limiter's state, including "not paused" when `DisableSpeedLimiter` is false);
  - sets gravity through `GravityScale`, and sets `JumpZVelocity` and `JumpMaxHoldTime` so the game's own first jump matches the mod's;
  - logs each of the first 20 hops (fps, updates per frame, take-off and landing speed, air time, view turn, keys, cuts) and a status line every 10 s.
- **Camera.**
  - When first person may be on (`view.lua`): Unreal shows the view target's first active camera component, in the order `K2_GetComponentsByClass` lists them (`AActor::CalcCamera`), or its eyes if none is active. First person waits while the view target isn't the character, during dialogue (`pc.BP_DialogueSystemComponent:IsInDialogue()`) and cinematics (`pc.BP_CinematicSystem.IsPlayingCinematic`, `IsInCinematicTransition()`), asked every 0.25 s, and while the camera the engine picks isn't an exploration camera: the one the character's `GetMainCamera(out)` returns (`out.MainCamera`, or any object UE4SS put in the table), or one named in `CameraComponents` (`Main_CineCamera`, `MainCamera`). 0.2 read `out.MainCamera_0`, the dump's name, which UE4SS never fills. 0.1 waited for `MainCamera:IsActive()`, which is probably never true in E33: the exploration camera is most likely `Main_CineCamera`. Activity is read from `bIsActive`, or `IsActive()` if UE4SS can't read it. The list is read again every 0.5 s, and at once when the camera shown stops being active or one before it starts.
  - `CameraMethod "engine"`: Unreal's `FirstPerson` camera style, the view from `GetActorEyesViewPoint` (the location plus `BaseEyeHeight`), with the control rotation and `DefaultFOV`, and no camera modifiers. `CameraStyle` is not a UPROPERTY, and E33's reflection data confirms it is missing there. So the mod calls `PlayerController:ClientSetCameraMode(FName)` every frame (it can't read the style back) and restores "Default". Reading and writing the field is kept for engines that reflect it. Shakes aren't played without modifiers, so `StopAllCameraShakes(true)` runs at each refresh. This loses the game camera's post-process and DoF, and the audio listener stays at the game's camera. It waits while the camera manager's `PendingViewTarget.Target` is set: `GetViewTarget` already returns the pending target during a blend, and the style applies to the outgoing target too (only `ACameraActor` bypasses it), so a plain actor holding a camera (sneaking, free aim, pre-cinematic) would be shown from its root. Only unpaused time counts: the camera manager doesn't blend while the game is paused. A blend that lasts over 3 s isn't waited for again until the camera manager no longer blends to the character (checked on every frame the mod acts, whether first person is on or not, so not while it is off or settling).
  - `CameraMethod "game"`: the engine's view camera is taken off its arm with `K2_AttachToComponent(capsule, None, SnapToTarget, SnapToTarget, KeepRelative, false)`, placed at `(0, 0, eye)` with `K2_SetRelativeLocationAndRotation(…, false, {}, true)`, `bUsePawnControlRotation = true` (the view then turns with the control rotation at view time) and `SetFieldOfView`. A cine camera's `FocusSettings.FocusMethod` is set to 3 (Disable), and the camera controller's `EnableDynamicCameraFocus` and `EnableCameraShakeWhenMoving` to false (again at each refresh, so the game's later value is what comes back). `K2_AttachToComponent` returning false gives up, instead of being taken for the game re-attaching. Every frame the parent, the relative location and the FOV are checked; what the game wrote meanwhile (re-attaching, a new camera setting, a new FOV) becomes what is put back. After a re-attach, the relative location is only taken if it isn't the mod's own `(0, 0, eye)` (an attach that keeps the relative transform leaves that), and the FOV is judged as on any frame if the view was worked out since the mod's last set, paused or not; before that, a reading other than the mod's value (or its learnt limit) is the game's. 0.2.2 skipped paused frames there and lost the game's FOV. The FOV the mod's value becomes is known at once for a plain camera. A cine camera works it out from a focal length clamped to its `LensSettings` when the view is computed (assumed before the view is built, so setting the mod's value again shows nothing for a frame). So for it, it is learnt from readings taken after a view update (the mod counts the frames that weren't paused; a value set while paused is read only after one): a reading of `FieldOfView`, or exactly the same other reading twice with the mod's set again in between (the lens can't go further, and gives the same value each time; the steps of a game blend that eases in or out can be smaller than the 0.05° tolerance). A reading that changed in between was the game's own. Until the next reading judges it, the newest isn't what release puts back: while the value is learnt (after a move or a recheck), a release within two frames of the game's last change, or in the pause it was read in (a re-attach's), puts back an earlier value, with a lens limit possibly the lens's own (0.2.2, which took an easing blend's tiny steps for a lens limit, had the blend's last value a frame sooner). A game value held for two frames or more as the camera is moved reads like a lens limit: the check at the next refresh after the hold ends finds it out, and release then puts the held value back if the lens lets the mod's value through, or else the value from before the move. 0.2.2 took two readings within 0.05° for a lens limit, so a game blend easing in as the camera moved was learnt as one, and with a real lens limit the mod then set its FOV every frame and put back the lens value. A learnt limit is checked again at each refresh, in case it was the game holding its own value, and logged once when it is seen again (the line says the game may be holding its value). Once the mod's value is known, every reading that differs is the game's: remembered, and the mod's set again. 0.2.1 took the first reading after a move as the mod's, so a game FOV write as first person started won; 0.2 took the next reading after each re-set, so a game FOV animation of an even number of frames won. Release attaches it back to the remembered parent and socket (KeepRelative) and restores the relative transform, flags, FOV and focus.
  - `CameraMethod "auto"` (default): "engine" first; if it fails its check, "game", and "game" from the start for that camera manager class for the rest of the session (until F5, F6 or F7). If "game" fails too, first person is given up.
  - The check: first person is assumed to work and the body is hidden at once; then the camera's location is compared with the eyes every frame until they match, and every 0.5 s after that. If the camera stays more than 50 cm away for 2 s (not while paused; a camera that got 25 % closer in that time gets another 2 s, for blends), or `ClientSetCameraMode` fails, the method has failed: everything is put back, the log says why, and first person stays off until F6 twice, F7, or a new character or camera manager.
  - Widen `ViewPitchMin/Max` and the rotation-limiter modifiers' `PitchMin/Max`. Eye height (0.78 × the capsule's half height) and `DefaultFOV` are set every frame when they differ, because the engine resets the eye height.
  - Hide the body by walking `AttachChildren` from the root: `SetOwnerNoSee` on primitives owned by the character, `SetHiddenInGame` on others, each part in its own `pcall`. Lights are left alone. Parts no longer attached are shown again. Parts that appear while first person is on are hidden from the next pass on (0.5-1 s later), not the pass they appear, and not if their owner is being destroyed. Known parts' full names are checked every 4th pass, and at once if the object is no longer valid or reads as shown: in UE4SS an old object's wrapper reads as valid again once a new object takes its address. A known part the game showed is hidden again, and shown is what comes back; a part the game showed since the last pass is left shown at release. A part the game shows and then hides again during first person comes back shown: once the mod has hidden it again, the game's hide can't be told from the mod's (hiding through the controller's `HiddenPrimitiveComponents` wouldn't share the game's flags; untested). The list of non-primitive addresses is cleared at release. In UE 5.4.4 a ChildActorComponent's actor gets no Owner, so the swappable skin and face meshes probably take the `SetHiddenInGame` route.
- **Jump input.** Keys are polled with `IsInputKeyDown` (`WasInputKeyJustPressed` only for mouse-wheel keys); the game's `JumpAction(bool)` hook is the fallback. That event may arrive as true then false, or, with Enhanced Input `Triggered` bindings, as true every frame with no release. `input.lua` detects the repeating form from frame numbers. The default movement keys are W A S D only (8 polls a frame less than with the arrows).
- **When the mod acts.**
  - Only for `BP_jRPG_Character_World_C`, and not when `bIsWorldMapPawn` is set.
  - Off in battle (`IsInBattle`, `IsInBattleBeginTransition`).
  - Nothing happens while the controller's `IsChangingArea` is set (everything is given back as it starts), nor for 3 s after a new level, character or area: E33 mod authors found crashes from touching just-spawned objects after loads.
  - Movement only in Walking, NavWalking or Falling, and not when move input is ignored or `CanAddMovementInput` is false. The movement step is skipped while paused or during root motion. A paused frame keeps the movement's state (`movement.hold`): Unreal moves nothing while paused, so a landing just before a pause is still handled after it and a hop goes on. What the mod wrote isn't checked after a pause, because on the frame the game pauses from the controller's own input, Unreal still moves the character once, with the game's input (0.2.4 lost the landing then, so that hop on a moving platform regained the platform's speed).
- **Restoring.** Every changed value is remembered together with the object's address and full name, and put back only if the object is still the same one. A value the game writes while the mod is active (ALS's gait speed, the game's speed for an area, the engine's eye height, the game camera's FOV) replaces the remembered one, so the game's latest value comes back. The mod doesn't ask ALS to set its speed again, which would lose an area's speed. Once known, a value is only read and compared each frame; full names are checked again at the 0.5 s refresh. When the world (the controller's `GetWorld`) changes, the old level's objects are gone: everything is forgotten without touching them. A new character in the same world is put back as usual.
- **UE4SS mods restart.** It drops the mod's Lua state without warning. So every change is also listed in the shared variable `HL1Movement.changes` (`journal.lua`: kind, full name, id, value; kinds `prop`, `hide`, `tick`, `curve`, `style`, `attach`). The new copy reads it at load and puts it back on its first frame, finding each object with `StaticFindObject` on the path in its full name, before it does anything else.
- **Report.** `diagnostics.lua` writes a report 3 s after first taking over, 10 s after taking over if first person still waits for no expected reason, when first person is given up, and on F8: the cameras in the engine's order with tags ([engine view], [GetMainCamera], [exploration], [closest to the view]) and their picture settings (for cine cameras also the lens's focal-length limits and the filmback), the spring arms, the movement values that limit speed, what the character stands on (`GetMovementBase`, `GetImpartedMovementBaseVelocity`, the game's own `IsAttachedToMovingPlatform`), the game's keys for its actions (`InputBlueprintHelpers.TryFindKeysForEnhancedInputActionName`), and the counts of what the game did. It only uses the controller the frame hook got.
- **Spreading the work.** The camera's 0.5 s refresh (pitch limits, hiding, shakes), the camera list's 0.5 s rescan and the movement's 0.5 s refresh fall on different frames: whenever first person starts (also on a new camera manager), the rescan is moved to 0.25 s and the movement's refresh to 0.125 s after the camera's, and when the movement starts again while first person is on, its refresh goes 0.125 s after one of the camera's. Each counts its next run from when the last was due, not from the frame it ran on, so uneven frame times don't bring them together (0.2.2 counted from the frame, and they met within minutes). A rescan because the camera shown changed doesn't move them. A frame longer than 0.125 s, the first frame of first person and the frame the movement starts can still carry two of them.
- **Units and defaults.** Settings are in Half-Life units, with `UnitScale` 2.5 cm per unit. The defaults are Half-Life 1's cvars, auto hop is on, and `BhopCap` is off. As in Half-Life, the jump speed is fixed (`JumpHeight` is reached at `Gravity` 800), so less gravity jumps higher.

## About the game (from research, not yet confirmed in the game)

- UE 5.4.4. The exe is `Sandfall\Binaries\Win64\SandFall-Win64-Shipping.exe`. There is no anti-cheat, no VAC and no Denuvo. The last patch was 1.5.6 (June 2026).
- The character is `/Game/jRPGTemplate/Blueprints/Basics/BP_jRPG_Character_World.BP_jRPG_Character_World_C`, built on ALS-Community (`ALSV4_CPP`), with `ALSCharacterMovementComponent` (Sandfall's fork, with nav-walking settings). The controller is `BP_jRPG_Controller_World_C`, also used in battle. Battles take place in the same world, with separate combatant actors. The world map uses other characters.
- Cameras: the character has `Main_CineCamera` (UCineCameraComponent) and `MainCamera` (UCameraComponent), with spring arms `SmartSpringArm_MainCamera` and `CharacterSpringArm`, 11 `CineCamera_Dialogue*` components and `ShoulderCam`. `GetMainCamera(out MainCamera)` names one of them (the dump says `MainCamera_0`; the game's own call sites name the pin `MainCamera`); every game camera system goes through it, and the camera controller casts it to a cine camera, so it is probably `Main_CineCamera`. Sneaking, aiming and pre-cinematic cameras are separate actors (view-target changes). The controller's `UpdateCameraViewTarget` picks the highest-priority camera override, else the pawn. `BP_CameraControllerComponent` runs config blenders (only during transitions), recentering, dynamic DoF focus on the character mesh and a shake while moving; `UpdateSpringArmLength`, sprint timelines, look-ats and crouch rewrite the arm and FOV.
- E33's dump of `APlayerCameraManager` has no `CameraStyle` property (an 8-byte gap where UE 5.4.4 keeps it). `APlayerController` has the UFunctions `Camera`, `ServerCamera` and `ClientSetCameraMode`; none is BlueprintCallable, so the game's Blueprints can't change the style. The camera manager is `BP_PlayerCameraManager_C`, based on `AExtendedPlayerCameraManager`, which adds no fields and only overrides `ShouldPlayCameraShake`. A C++ override of `UpdateViewTarget` wouldn't show in a dump; the console command `camera firstperson` tests it. No public E33 mod uses the style; working E33 camera mods change the game's rig.
- The pitch limiters are `CameraModifier_RotationLimiter` modifiers (`PitchMin`/`PitchMax`, and `YawMin`/`YaxMax`, misspelled in C++), one of them added for climbing.
- Movement: ALS's `bRequestMovementSettingsChange` is a `uint8`. The character's `OnCharacterMovementDataQueueUpdated` writes `MaxWalkSpeed`. The speed limiter's `LimitVelocityIfNeeded` clamps to `GetMaxSpeed()`, and its `OnMovementModeChanged` is bound to `ACharacter::MovementModeChangedDelegate`, broadcast inside every `SetMovementMode`. Another E33 mod (co-op) measured that writing `MaxWalkSpeed` directly didn't change its pawn's speed (input-driven movement); only `CurrentMovementSettings` speeds plus the request flag did. Look input goes into the control rotation (`AddControllerYawInput`); move input goes through ALS's name-bound Enhanced Input actions during `PlayerTick`; E33's own input manager polls with `IsInputKeyDown`.
- The controller has `BP_DialogueSystemComponent` (`IsInDialogue()`), `BP_CinematicSystem` (`IsPlayingCinematic`, `IsInCinematicTransition()`, `IsPlayingSequence(out)`), `IsChangingArea`, `CameraOverrideActor` and `HasCameraOverride(out)`.
- The character also has: a torch (`AttachTorch`, `UnattachTorch`, `TorchActor`, `Torch_SpringArm`); a double jump (`SD_CharacterWorld_DoubleJump`, `JumpCounter`); capabilities (`CharacterCapabilities`, `IsCapabilityAllowed`); moving platforms (the flag `IsAttachedToMovingPlatform`, set by `SetIsAttachedToMovingPlatform`, which, by the dump's locals, scales the cloth simulation of the character's skeletal meshes).
- The pause menu uses `SetGamePaused`. The game's own gameplay pause also locks input, which `CanAddMovementInput` catches. E33 shows "The UE-Sandfall Game has crashed / Fatal error!" often even without mods (DX12, drivers, save loads). UE4SS writes `ue4ss\crash_*.dmp`; Unreal writes `%LOCALAPPDATA%\Sandfall\Saved\Crashes`. Remote Desktop caps games at 30 fps and handles relative mouse input badly.
- Still unknown:
  - whether `ClientSetCameraMode("FirstPerson")` takes effect, and which camera `GetMainCamera` returns;
  - whether the game's speed cap follows `MaxWalkSpeed`, and when the limiter starts again;
  - whether landing rolls use root motion, and whether `CanJump` is true in exploration;
  - whether the picture changes with the engine's view (post-process settings on the camera component);
  - the cause of the crash in the second test (over Remote Desktop, seconds after gaining control).

- 0.1.1 made the log explain itself: state lines with reasons (`log.state`), a line before the first use of each kind of change (`log.first`), automatic reports and a status line every 10 s.
- 0.2 follows a research pass on E33's camera rig, input, the crash and other E33 mods: the camera rule from the engine (the likely reason first person never started), the game-camera fallback, 100 Hz movement updates, KeepSpeed and the limiter checked every frame, the platform-only jump velocity, safe hook registration, the 3 s settle and area-change wait, forgetting a destroyed level, cheaper frames, and a report that answers the open questions.
- 0.2.1 fixes what a five-part review of 0.2 (UE4SS API, engine, logic, crashes and cost, tests and docs, each finding checked by a second reviewer) confirmed or found likely: `GetMainCamera`'s out key, the game-camera FOV (animations, lens limits, moves at activation), walls taken for speed cuts, cuts below 20 %, the re-attach location, hidden parts at reused addresses and parts the game shows, the engine view during blends, `bStayBasedInAir`, F8 during loads, `PhysicsRate` above 250 and the limiter text. Refuted: registering hooks from key callbacks is a crash risk (UE4SS does its own object lookups, and moving them to `ExecuteInGameThread` could run `RegisterHook` inside `script_hook` with the ProcessEvent method).

Not tested in the game yet.
